# 审核提示词：插件结构草案

用法：把下面「提示词」那一段整段贴给审核者（这一轮是 neon）。审核者那边如果有联网搜索、深度研究一类的开关，先打开。

---

## 提示词

你是一名有经验的游戏设计和游戏工程审核者。请审一份草案：`设计/插件结构-草案.md`。项目是一个卡牌肉鸽，暂叫 code00，原型在 `原型/neon/`（浏览器、原生 JS、Canvas 2D）。

**这次为什么审**
- 用户刚定了「先回到核心」：原型打开只有宝石牌打怪，外圈（功能牌、加成、队友、装备、工会、任务、大厅、走一趟）入口关掉，代码留着。
- 用户打了核心以后说「基础机制和打怪问题不大」，现在的问题是**怎么一点一点往上加功能**：要像插件一样往核心上加，随时可插拔，更新、删除都行，不要一眼看上去乱成一锅。
- claude 照这个写了一套「核心 + 挂点 + 插件 + 开关表 + 自动检查」的设计。用户看了说「**我感觉设计的有问题**」，没说哪里有问题，所以请你找。
- 草案第一节是用户的想法，第二节是现在代码的事实，第三节是 claude 的设计，第四节是 claude 自己拿不准的 10 处，第五节是要你回答的问题。

**先读这些**
1. `CLAUDE.md`：项目的规矩（回复中文、不取名、用词避开套路字、模块解耦只在 `app/` 组装、怪和技能要跟用户一起定……）。
2. `设计/插件结构-草案.md`：要审的东西。
3. `设计/做原型的方法.md`：为什么先做核心、查过的资料。
4. `设计/设计.md`：第 7 版开头、10.4 开头「先回到核心」、第 10 节（工程：模块怎么分、约定）。别的节需要再翻。
5. 代码，至少看这几个，核对草案第二节说得对不对：
   - `原型/neon/modules/battle-rules/engine.js`（核心战斗引擎，1700 行）；
   - `原型/neon/modules/shared/timings-actions.js`、`rule-keys.js`、`contracts.js`（时机、动作、改规则的规则名、约定）；
   - `原型/neon/modules/content/index.js`、`buffs/buffs.js`；
   - `原型/neon/app/main.js`、`app/scenes/hub-scene.js`、`app/scenes/core-scene.js`；
   - `原型/neon/tools/boundary.test.js`、`tools/core-sim.js`。

**不要**
- 不要改代码，不要改 `设计/` 里的文件，不要提交。只写审核结果。
- 不要读 `旧/` 和上一级的 `../异能卡牌/`（例外：`../异能卡牌/玩法/核心玩法/战斗界面-色块原型.html` 是用户自己做的战斗原型，可以看交互）。
- 不要推翻用户已经定的：先做核心、外圈后加；出牌只能拖、只接链尾、不能改顺序；模块解耦、只在 `app/` 组装；原型不用 Electron、全用色块。

**要查资料，别凭空设计**
- 下判断之前先查：同类游戏和框架是怎么做「往核心上加功能」的，效果好不好，开发者怎么说。值得查的方向（不限于这些）：
  - 杀戮尖塔的遗物、状态挂点，和它的改游戏工具（BaseMod、StSLib）；
  - 小丑牌的小丑计分顺序、`calculate` 加上下文的做法，和它的改游戏工具（Steamodded）；
  - 别的卡牌肉鸽（怪物火车、Cobalt Core、Inscryption……）怎么组织遗物、规则改动；
  - 通用的游戏工程做法：事件总线、动作队列、数据驱动的效果、功能开关（feature toggle）、组件式；它们在小团队原型阶段的利弊；
  - 原型阶段该不该先抽框架（提前抽象的坑）。
- 每条意见都写**依据**，分两种：
  - **有出处**：哪个游戏、哪个框架、哪份资料怎么做、怎么说的，附链接或出处；
  - **我的判断**：没有出处的标「我的判断」，写清推理。
- 不确定就写不确定，不要编出处。不能上网就在总评里说明。
- 借鉴是为了找问题、找改法，不是照搬。

**请重点看**
1. 草案第一节把用户的想法归纳对了没有？R3「一眼看上去不乱」更像说代码，还是说游戏本身（画面、系统）？两种都有可能的话，各要怎么做？
2. 方向对不对：「核心 + 挂点 + 插件 + 开关表 + 自动检查」。原型阶段做这一套是不是太重？如果太重，**最小够用**的做法是什么？
3. 草案第四节 claude 拿不准的 10 处，每处怎么看、有没有更好的做法：做得重不重、挂点粗细、两个插件改同一个数的先后、插件之间的依赖、预览空跑、画面要不要插件化、核心的边界、存档、「随时可插拔」是对开发还是对玩家、旧外圈先全搬还是轮到再搬。
4. 草案第二节说的代码事实，核对一下有没有说错、漏掉的。
5. claude 没看到的问题。
6. 照用户的要求，你会怎么安排接下来几步？

**交回什么**
- 写成一个文件：`审核/neon/2026-11-24-插件结构草案.md`（你能写文件就直接写，写不了就整段贴出来，用户会存）。
- 格式：
  1. **总评**：几句话说这套设计能不能用、最大的问题是什么。
  2. **一条条意见**：每条写「问题 → 依据（有出处 / 我的判断）→ 建议怎么改 → 对用户的想法有没有冲突」。
  3. **要用户拍板的**：分成两三块，每块给两三个真不一样的候选，加上你的倾向和理由。
- 用中文，用大白话，少用术语；必须用的术语第一次出现时解释一句。用户不是写程序的人。
